# Active driver architecture

Runtime code consists of `src/init.lua` (SmartThings lifecycle and capability handlers), `src/twinkly/discovery.lua` (bounded UDP discovery), `src/twinkly/api.lua` (authenticated HTTP requests), `src/twinkly/scenes.lua` (scene validation and selection), and `src/twinkly/utils.lua` (login challenge generation).

A discovery response is verified with unauthenticated gestalt data before a LAN device is created. The MAC address forms a stable network ID. Discovery updates the stored IP for a known device; only legacy timestamp-based placeholders are matched by IP. Duplicate replies or repeated scans for one MAC request at most one creation while registration is pending. If registration does not complete, a new scan may retry after 30 seconds. A reused IP cannot merge two MAC-based devices.

The API client caches a token per IP. It logs in with a 32-byte base64 challenge, verifies the returned token, and retries one operation after HTTP 401. It checks both HTTP status and Twinkly's JSON `code` field. Each socket operation is limited to 3 seconds and receives the remaining part of an 8-second budget shared by login, verification, command and any authentication retry. Response bodies are capped at 256 KiB before JSON decoding.

The driver emits capability events only after successful responses. If polling cannot reach a device, discovery runs in lookup-only mode at most once every 30 seconds, and refresh retries when it finds a changed IP. A manual IP preference skips broadcast rediscovery because it overrides the discovered address. Clearing a manual IP discards the stored manual address and resets the cooldown. `init` sets up one periodic timer per device using `call_on_schedule`; `infoChanged` replaces it only when an IP or polling preference changes, and `removed` cancels it. SmartThings automatically calls `init` after `added`, so there is no redundant `added` handler.

The optional `scene` preference is a small command surface that requires no cloud-side custom capability. Scene IDs are checked against the device's effect count or uploaded movie list before use. Effects and movies use the API's `unique_id` as their persisted identity when available, so numeric slot changes do not silently select another scene. A scene choice made while the device is unreachable is persisted once and retried on a later successful poll or on command; invalid and unavailable choices are discarded. An explicit off or color command clears the pending choice. Successful selections are stored for on/off restoration; polling also observes scene changes made in the Twinkly app. If a write times out after it may have reached the device, the driver reads the actual state before reporting it.

The first brightness or color command is sent immediately. Follow-up slider commands keep only the latest value and are sent at most once every 120 ms for brightness or 150 ms for color, including during continuous drags. Each color update makes at most one `/led/color` write followed by one mode write. The latest requested hue and saturation remain available while the network call is in flight, so separate `setHue` and `setSaturation` commands compose correctly. Failed color writes discard that unconfirmed target. Polling skips brightness or color readback while a newer value is queued or being written. Off, On, scene changes and removal cancel queued slider updates; generation checks prevent superseded in-flight responses from emitting stale events.

During creation, discovery reads `/xled/v1/fw/version` and chooses a switch, dimmer, or color profile according to documented firmware support. Existing profile names remain available for SmartThings package updates.

This layout follows the [SmartThings driver structure](https://developer.smartthings.com/docs/devices/hub-connected/driver-components-and-structure) and [LAN programming guide](https://developer.smartthings.com/docs/devices/hub-connected/lan). There is no `search-parameters.yml` because Twinkly discovery uses its own UDP broadcast protocol rather than mDNS or SSDP.
